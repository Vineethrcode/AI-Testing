7. DOCUMENT INGESTION
============================================================

When a document is uploaded:

1. The document is received by the backend.
2. Text is extracted.
3. Text is cleaned.
4. Text is divided into chunks.
5. Each chunk is sent to nomic-embed-text through Ollama.

The metadata contains information such as:

- documentName
- documentId
- chunkId
- page
- text

The application exposes a document-upload/indexing endpoint.

8. INITIAL CHUNKING PROBLEM
============================================================

Originally, chunking was mainly character-based.

This created a problem with QA documents.

A Test Case could be split between chunks.

For example:

Chunk 1:
Test Case ID: 24
Test Case Name: ...
Description: ...
Expected Result: ...

Chunk 2:
Actual Result: ...
Status: Pass
Severity: ...
Priority: ...

This means retrieving only one chunk could give the LLM incomplete information.

============================================================
9. TEST-CASE-AWARE CHUNKING FIX
============================================================

We modified chunking to recognize:

Test Case ID: <number>

as a logical boundary.

The system attempts to keep a Test Case record together.

Conceptually:

Test Case ID: 20
    ↓
TC-20 record

Test Case ID: 21
    ↓
TC-21 record

Test Case ID: 22
    ↓
TC-22 record

If an individual Test Case block is too large, fallback splitting can still be used.

If a document does not contain Test Case IDs, generic chunking is used.

DO NOT unnecessarily modify chunking again unless a real test proves there is still a chunking problem.

============================================================
16. CORRECT EXACT TEST CASE ID RETRIEVAL
============================================================

We changed the implementation to use Vectra's:

listItems()

instead of relying entirely on semantic similarity.

The retrieval flow became:

User question
      ↓
Detect Test Case ID
      ↓
TC-22
      ↓
Vectra listItems()
      ↓
Inspect all indexed items
      ↓
Exact text match
      ↓
Retrieve matching records

The exact matching uses a regex pattern conceptually similar to:

Test Case ID:\s*<ID>(?!\d)

The negative lookahead helps prevent partial matching.

For example:

22

should not accidentally match:

220
222

The exact lookup searches across ALL indexed documents.

============================================================
17. QUESTION-LEVEL TEST CASE ID EXTRACTION
============================================================

Another problem was discovered.

Initially, IDs were extracted only from semantic search results.

That was backwards.

If the user asks:

"Give me details of Test Case ID 24."

the question itself already tells us the required ID.

Therefore, the retrieval system now extracts Test Case IDs from:

1. The user question
2. Initial semantic retrieval results

These IDs are combined/deduplicated.

Then exact lookup is performed.

============================================================
20. GROUNDING PROBLEM
============================================================

We encountered a score-normalization issue.

Exact results were initially assigned:

score: 1

But later the code normalized scores using something conceptually similar to:

1 - result.score

So:

1 - 1 = 0

The exact match could therefore become score 0.

The grounding threshold could then incorrectly reject an exact match.

This was fixed so deterministic exact matches are treated as high-confidence results.

We did NOT simply remove grounding.

We did NOT set the grounding threshold to zero.

The goal is still to prevent the LLM from answering confidently when the retrieved context doesn't support the answer.

============================================================
28. TOP-K LIMITATION
============================================================

Our semantic retrieval uses a limited number of results.

This creates a problem for questions such as:

"Which test cases failed?"

because the user wants ALL matching cases.

Top-K semantic search is designed to return the most similar chunks, not every record satisfying a condition.

Simply changing:

topK = 5

to:

topK = 20

might improve recall but is NOT considered the complete solution.

============================================================
29. IMPORTANT ARCHITECTURAL DISTINCTION
============================================================

There are different types of questions.

TYPE 1 — Specific entity query

Example:

"Give me details of Test Case ID 24."

Best approach:

Detect TC-24
→ exact deterministic lookup
→ retrieve related records
→ LLM

This currently works.

TYPE 2 — Broad structured query

Example:

"Which test cases failed?"

This requires something closer to:

Find ALL relevant execution records
→ extract IDs/status
→ validate against actual Test Case records
→ return the complete valid set

This should not depend solely on Top-K semantic search.

TYPE 3 — Feature/semantic query

Example:

"What test cases are related to login?"

This requires good semantic retrieval plus relevance filtering/reranking.

30. SECOND CHAT'S MAJOR DISCOVERY
============================================================

The second chat inspected the current server/index.js and identified a deeper problem in the status retrieval branch.

The current status branch was doing something conceptually like:

Find valid IDs from test_cases.md
        ↓
Scan all documents for non-Pass records
        ↓
Match IDs
        ↓
Send both base record and supporting record to LLM

The problem is that matching the same ID does not necessarily prove the supporting record is the correct record for that Test Case.

This is how we got situations such as:

- correct TC-96
- incorrect TC-57/58
- Pass login cases appearing in a failure query

The deeper issue is that we were asking the LLM/retrieval logic to infer relationships that the application should establish beforehand.

============================================================
32. NEW METADATA FIELD — testCaseId
============================================================

The planned change is to add:

testCaseId

to the metadata of every indexed chunk that belongs to a Test Case.

Example:

{
  documentName: "test_cases.md",
  testCaseId: "96",
  text: "...",
  ...
}

Execution records can then have:

{
  documentName: "test_execution.md",
  testCaseId: "96",
  text: "...",
  ...
}

Observation records can similarly have:

testCaseId: "96"

Then records can be joined using:

testCaseId = 96

instead of relying on arbitrary text similarity.

============================================================
33. WHY testCaseId METADATA IS IMPORTANT
============================================================

Without structured metadata:

The system repeatedly tries to infer:

"Does this chunk belong to TC-96?"

With structured metadata:

The application knows:

testCaseId = 96

Therefore:

TC-96
→ base Test Case record
→ execution record
→ observation/defect record

can be connected deterministically.

This is much more reliable.

41. IMPORTANT LESSONS LEARNED
============================================================

Do not immediately blame the LLM when an answer is wrong.

First inspect:

Did retrieval find the correct information?

RAG quality depends heavily on retrieval quality.

Also:

Semantic similarity is not exact matching.

A vector database does not automatically understand:

"Give me every failed test case."

That requires structured retrieval logic.

Also:

The LLM should not be responsible for deciding relationships that the application can establish deterministically.

If the application knows:

testCaseId = 96

it should use that rather than asking the LLM to infer that two arbitrary chunks refer to the same test case.
